# 2026-09-18

## 缓存与缓存找回策略梳理（只读代码审查，未改代码）

涉及文件：`server/core/cache/unifiedCache.ts`、`memoryCache.ts`、`server/core/services/searchService.ts`、`policyService.ts`、`services/index.ts`、`server/utils/executeSearch.ts`、`searchRequest.ts`、`nuxt.config.ts`。

结论要点：
- 只有一层服务端内存缓存（进程内），无 Redis / 无持久化。`UnifiedCache` 由 `SearchService` 单例（globalThis key `__panhub_search_service__`）持有，PM2 为 `fork / instances: 1`，所以缓存不会跨进程。
- 缓存键 = `search:search:keyword:<规范化kw>:sources:<排序来源id>:config:<来源revision|searchSettings版本|模板版本>`；配置版本变化即自然失效。
- 缓存项按「来源」粒度存 `{status, results, warning}`。命中时只复用 status=success 的来源，其余重跑 —— 这就是「缓存找回」的实际语义。
- 请求带 `channels`（自定义频道，ephemeral）时 `cacheAllowed=false`，读写全部禁用；`refresh=true` 只跳过读，仍会写。
- 策略参数来自 `policy_settings`：`cacheTtlMinutes` 1–10（默认 10）、`cacheMaxMemoryMb` 16–512（默认 100）。改 TTL 触发 `clearAll()`；改容量只触发立即 LRU 淘汰。
- 有过期来源单飞（in-flight 去重）机制，键相同并发请求合并为一次执行。
- HTTP 层统一 `no-store`（/api/search 全路径 + SSE），客户端 `$fetch` 亦用 `cache: "no-store"`，仅 `/_nuxt/**` 有 1 年 immutable 缓存。

发现的可改进点（尚未动手）：
1. `refresh` 参数已实现但前端无任何调用点，用户无法主动强制刷新。
2. `clearAll()` / `forceCleanup()` 除定义外无调用者，后台没有「清空搜索缓存」入口。
3. `CacheNamespace.HOT_SEARCH` 是死代码（热搜走 SQLite `hot_searches` 表）。
4. `refresh=true` 时不读旧缓存，`nextStates` 全量初始化为 failed，本轮失败的来源会把原先成功的缓存改写为 failed；且每次都是整条覆盖写，部分命中会把命中来源的 TTL 续期。
5. `estimateSize` 每次 `set` 都 `JSON.stringify` 整个载荷，结果集大时是纯 CPU 开销。

## 第二轮：全项目缓存盘点（同一天，只读）

除了搜索缓存，项目里另有多套独立缓存/内存状态，各自策略不同：
1. `managedResourceService.ts` 本地资源关键词缓存：TTL 30s、上限 256 条、**满了整体 `clear()`（非 LRU）**、任何写入 `invalidateSearchCache()` 全清；键只做 `trim()`（未做 NFKC/小写规范化，与来源缓存键的 `canonical()` 不一致）。
2. `sqlite.ts` 预编译语句缓存：上限 256，真 LRU（命中 delete+set 重排）。
3. `rateLimit.ts` `MemoryRateLimiter` × 3（admin / search / credentialLogin）：MAX_BUCKETS 10000，超限先 prune（1 小时龄）再按插入顺序删旧。
4. 源健康状态：内存 `SourceHealthChecker` + SQLite `source_health` 持久化（构造函数 importSnapshot 恢复），搜索期间按来源排队、结束时一次事务 flush。
5. `pinnedTransport.ts` 出站传输能力探测缓存：进程内永久 + loading Promise 单飞。
6. `wechatQrLoginService.ts` access_token 缓存（expiresAt + forceRefresh）。
7. 前端 localStorage 仅存主题；搜索结果无客户端缓存；`useSearch` 的暂停/继续 = 重发同一 POST（不带 refresh，故第二次基本命中缓存）。

新发现（优先级高于上一轮的 LRU 细节）：
- **transform 脚本无编译缓存**：每次来源执行都 `validateSourceTransformCode()`（内部 `new Script` 编译）→ `executeSourceTransform()` 再 `new Script` ×2（创建函数 + 调用），单来源单次搜索 3 次 V8 编译；10 个来源就是 30 次。`definition.manifest.version`（`cfg-<hash>`）已传入 transform 定义却没被用作缓存键。
- **缓存键与策略解析每次全量查 SQLite**：`getUserPolicy()` 3 条查询 + `getUnifiedSourceVersion()` ≈ 7 条（config_revisions / search_settings / system_settings / getSearchSettings 3 条 / source_template_settings）+ `listUnifiedSources()` 每次 2 条且每次搜索被调用两次（executeSearch 一次、syncRuntimePolicy→pruneStaleHealth 一次）。一次「命中缓存」的搜索在返回前仍有 15+ 条 SQLite 查询 + 全量 JSON 解析 + 正则校验。缓存省了出网，没省掉键计算。
- `performSearch` 里的写缓存条件 `allSources.every(source => source.enabled !== false)` **恒为真**——`resolveSources()` 已过滤掉 `enabled === false` 的来源，属冗余判断。
- `transformFunctionSource()`（validation.ts:234）与 `createTransformSource()`（runtime.ts:67）是同一逻辑的两份拷贝，存在校验形态与运行形态分叉的风险。
- `getConfiguredSource()` 内部把 `read()` 调用了两次（存在性检查 + clone）。
以上均未修改代码。
