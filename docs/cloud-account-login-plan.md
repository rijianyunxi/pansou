# 网盘扫码连接与凭证托管方案

日期：2026-10-02。状态：设计方案，尚未实施；平台登录接口需要真实账号联调。

## 1. 目标与范围

把后台五家网盘的账号配置统一为“连接账号 → 扫码确认 → 选择目录 → 开启功能”。普通配置流程不要求用户复制 Cookie、access_token、账号 ID 或设备签名。系统负责获取凭证、识别账号、保存和续期，确实需要用户处理时显示重新授权或安全验证入口。

首版延续现有范围：管理员配置的服务端账号，每家网盘一个当前账号。扫码成功不自动打开转存、分享或清理开关。各网站用户的个人网盘、多账号轮询、跨网盘搬运不在首版范围内。

扫码授权、访问令牌续期、设备会话维护分别由各平台适配器实现。一次扫码不能保证永久在线，二维码有效期也不等于访问令牌有效期。

## 2. 管理员使用流程

五家网盘使用同一套账号卡片，展示网盘名称、已连接账号、连接状态、最近验证时间及操作入口。账号昵称可显示，账号 ID 默认脱敏；凭证不回显。

1. 点击“连接账号”，弹出二维码和对应 App 的扫码说明。
2. 展示等待扫码、等待确认、正在验证、已连接、二维码过期等状态。过期提供重新生成入口；关闭弹窗取消当前登录会话。
3. 后端确认登录后获取账号身份，并读取根目录验证访问能力，成功才提交新凭证。
4. 首次连接成功后引导选择项目专用目录、保留时间和功能开关。
5. 已连接账号提供“检测连接”“重新授权”“更换账号”“断开连接”。手动凭证导入放入折叠的“高级设置”，并说明该凭证能否自动续期。

重新授权要求平台返回的账号与原账号一致；扫到其他账号时提示使用“更换账号”。更换账号属于单独操作，提示旧账号尚有多少待清理产物，暂停该平台新写入并要求重新选择目录。原账号凭证在新账号验证失败时保持可用。

断开连接取消未完成登录会话和续期任务，并删除本系统持有的凭证；待清理任务和归属证据保留。平台全局注销不作为默认操作。

产品层展示五种连接状态：未连接、可用、暂时异常、需要验证、需要重新授权。“正在续期”只作为临时提示。后台分别记录身份验证、目录读取、续期能力和业务接口可用性，避免将“登录成功”解释为所有操作都有权限。

## 3. 平台接入路线与验证门槛

| 平台 | 拟采用的认证路线 | 托管内容 | 实施前需要确认 |
| --- | --- | --- | --- |
| 夸克 | 官方网页扫码会话 | 网页 Cookie、已验证账号 ID、服务端设备信息 | 扫码所得 Cookie 可用于现有 PC 转存接口；响应 Cookie 更新规则 |
| 百度 | 官方网页扫码会话 | 网页 Cookie、已验证账号 ID及网页接口所需令牌 | 扫码最终 Cookie 满足当前 BDUSS/BAIDUID 校验；目录、转存和清理接口兼容 |
| 阿里 | 与当前网页接口兼容的扫码登录 | access_token、refresh_token、有效期、账号 ID、drive_id、设备会话 | 网页令牌与开放平台令牌的接口权限差异；设备注册和签名续期机制 |
| 迅雷 | 优先接入官方网页扫码流程 | access_token、refresh_token、有效期、固定设备身份、captcha 状态 | 扫码是否能获得可续期凭证；客户端身份与现有 x-api-pan 接口匹配；风控挑战处理 |
| 光鸭 | 设备授权扫码流程 | access_token、refresh_token、有效期、账号 ID、设备信息 | 扫码授权客户端与当前存储接口兼容；刷新时是否轮换 refresh_token |

这些是接入路线，不是五家均已验证的承诺。已有阿里和光鸭客户端提供扫码、令牌维护参考；迅雷客户端提供访问令牌和验证码令牌刷新参考。百度、迅雷的最终扫码契约及所有平台的真实权限仍需联调。

阿里不得把开放平台的扫码结果直接套给当前网页接口；夸克不得把 TV 端 Token 当作网页 Cookie。账号、客户端、设备及业务接口必须来自同一兼容认证链路。

若某家稳定扫码链路暂时不可用，卡片明确提供“官方网页登录”或“手动导入”备用方式，并显示真实续期能力。不能用一个二维码按钮包装仍需手填多个字段的流程。

Cookie 平台只自动接收并持久化平台实际发出的更新。没有已验证的续期机制时，检测到失效就要求重新扫码，不承诺通过定时访问实现永久保活。

## 4. 后端模块划分

保留 Rust/Axum、PostgreSQL、Redis 和现有网盘业务适配器，新增独立的 `cloud_auth` 模块，不引入常驻浏览器作为首版必需依赖。

```text
账号卡片 / 扫码弹窗
          │
          ▼
管理员账号连接 API
          │
          ▼
cloud_auth：登录会话、凭证管理、账号识别、续期调度
     │                         │
     ▼                         ▼
各平台登录适配器           PostgreSQL 加密存储
     │
     ▼
官方登录与账号接口

目录 / 转存 / 分享 / 清理
          │
          ▼
cloud_auth.get_valid_credential()
          │
          ▼
现有 cloud_drive 业务接口
```

建议文件职责：

- `src/cloud_auth/mod.rs`：统一入口、平台能力和凭证快照类型。
- `src/cloud_auth/providers/`：各家的扫码、授权交换、身份读取、刷新和挑战处理。
- `src/cloud_auth/store.rs`：加密存储、凭证版本、账号绑定和刷新租约。
- `src/cloud_auth/sessions.rs`：短期登录会话及服务端轮询。
- `src/cloud_auth/worker.rs`：到期刷新、受控连接检测、会话回收。
- `src/handlers/cloud_accounts.rs`：管理员连接接口。
- `frontend/components/admin/CloudAccountCard.vue`、`CloudLoginDialog.vue`：统一账号交互。

`Drive::load()` 改为获取有效凭证快照，再建立业务请求头。续期后的请求必须使用新快照，避免 `Wire` 初始化时缓存的旧请求头继续被使用。现有设置接口在过渡期保留，保存也统一经过身份验证和凭证管理器。

## 5. 数据、版本与旧任务迁移

扩展现有 `cloud_account_settings`，保留每个平台一个当前账号的结构。增加以下信息：

| 字段组 | 内容与目的 |
| --- | --- |
| 账号身份 | 官方接口验证的 subject ID、存储空间 ID、稳定 account_key、昵称 |
| 凭证 | 加密后的平台凭证、格式版本、密钥版本、来源、是否可刷新 |
| 生命周期 | access/captcha 有效期、下一次刷新时间、最近成功刷新及身份验证时间 |
| 版本 | token_revision 表示凭证更新；binding_epoch 表示当前账号或存储空间切换 |
| 状态 | 连接状态、结构化原因码、失败次数及下次允许重试时间 |
| 租约 | 刷新任务 owner、租约截止时间和提交版本条件 |

新增 `cloud_login_sessions` 保存管理员所属登录会话、平台、用途、过期时间、加密的上游授权上下文、轮询时间和租约。登录会话短期保存，到期清除敏感上下文；登录事件日志不保存二维码链接、Cookie 或 Token。

新增账号历史归属映射，记录平台、官方验证身份、旧 account_key 及绑定验证时间。只保留必要元信息，不默认保存被替换账号的旧凭证；需要恢复旧账号清理时重新扫码。

现有 `credential_fingerprint()` 对百度、夸克计算整段 Cookie 的哈希，Cookie 更新会改变任务归属标识。必须同步改为稳定身份键，例如规范化编码后的 `provider + subject_id + storage_scope` 的哈希。阿里保留 drive_id 维度。

旧数据迁移按以下规则执行：

1. 对当前有效凭证读取官方账号身份，建立“旧 fingerprint → 验证身份”的映射。
2. 保留已有 `link_share_cache.target_account_key` 和清理证据；通过映射判断归属，避免批量改写任务与唯一索引。
3. 无法验证的历史 fingerprint 保持待验证，不凭昵称、手填 user_id 或管理员猜测合并账号。
4. 同账号刷新和重新扫码保留产物归属；更换账号或空间变更不会继承旧产物。

凭证采用 AEAD 加密（如 AES-256-GCM），绑定 provider、身份及格式版本作为附加认证数据。加密密钥使用服务端部署配置 `PANSOU_CLOUD_CREDENTIAL_KEY`，与数据库分开保存并支持密钥版本。迁移成功后清除原明文列；密钥备份属于部署备份的一部分。

迁移期间先发布支持新旧格式的读写代码，再迁移和清除明文。清除后不能回滚到仅认识明文格式的旧版本；回滚构建需保留加密读取能力。

## 6. 登录与凭证维护规则

扫码开始时建立当前管理员专属会话，服务端按上游建议间隔轮询，前端只读取本系统状态。上游要求放慢时遵循其间隔，不固定高频轮询。重复点击只保留最新有效会话；旧会话完成、已取消会话或过期会话不得覆盖当前绑定。

授权结果先进入暂存凭证，完成官方身份读取、基础访问验证以及账号匹配后，再原子提交到当前账号。提交必须检查会话状态、绑定版本和管理员权限；扫码过程中账号被其他管理员更换，原会话不能继续提交。

对于支持刷新令牌的平台，使用上游 `expires_in`、`expire_time` 等字段计算续期时机，临近到期提前刷新并加入少量随机偏移。未知有效期记录为未知，由适配器受控检测，不把猜测时间显示成平台保证。

刷新成功必须原子保存新 access_token、有效期和平台返回的新 refresh_token。只有平台契约允许且响应确实未轮换刷新令牌时，才保留旧 refresh_token。固定设备身份在首次授权时建立，此后续期保持一致；需要重建设备会话时由对应适配器处理。

同账号并发续期通过 PostgreSQL 租约串行执行，并用 token_revision/binding_epoch 条件提交；不在等待上游响应期间持有长数据库事务。旧租约返回结果不能覆盖新结果。若平台刷新令牌只能使用一次且请求结果丢失，标为续期结果待确认，遵循该平台的恢复契约，不能盲目重复消费刷新令牌。

请求失败处理：

- 确认访问令牌失效：允许一次受控续期，安全的只读请求最多重试一次。
- captcha/设备会话失效：交给对应平台修复，不能当作普通 access_token 过期。
- 平台要求验证码、短信或其他确认：显示“需要验证”及允许的官方验证入口。
- 网络错误或限流：保留凭证，退避重试，不立即判定账号失效。
- 403 或业务权限错误：区分风控、权限和身份失效，不一律循环刷新。
- 刷新凭证确认撤销或失效：显示“需要重新授权”，暂停依赖该账号的新写入。

新建目录、转存、分享、删除等写请求一旦发出，响应不确定时沿用现有确认与清理机制；不能因自动刷新而重复执行写操作。

凭证维护作为独立逻辑运行在 `serve` 和 `link-worker` 的生命周期中，由数据库租约防止多实例重复执行。它不受转存、清理或抓取开关影响；关闭内置业务 Worker 时，运行中的 API 仍能处理登录和必要续期。停机后重启先检查凭证期限再承接业务请求。

## 7. 与交付、清理的衔接

所有业务入口统一经过凭证管理器，避免目录接口、手动操作和后台清理各自实现刷新。

获取凭证与云端写操作遵守统一顺序：先完成必要续期，再获取现有平台写锁，检查绑定仍为同一账号及空间，并核对快照是否可用。发生版本竞态时在写请求发出前重新准备快照；持锁路径不反向等待正在申请写锁的凭证提交任务。

登录过期导致的清理等待不消耗“实际清理失败”次数，单独记录 `waiting_auth` 原因并暂停该账号相关任务。重新授权后，系统只恢复同一验证身份下因认证等待的任务；文件清单变化、归属不明或写入结果不确定的任务保持原有阻塞。

账号 B 授权成功不能恢复账号 A 的清理任务。恢复账号 A 后仍需检查清理租约、目录和文件清单、分享撤销进度，再执行删除。令牌更新不改变账号归属，账号更换则重新验证目录配置。

前台取链继续遵守现有约 5 秒响应窗口。首次登录、等待扫码、长期风控验证不占用取链请求等待时间；凭证准备无法在窗口内完成时返回原始链接，并在后台维护账号状态。已经发送的写操作继续确认并保留准确产物记录。

## 8. API 与访问边界

建议新增管理员接口（命名可在实施时与现有路由统一）：

| 接口 | 作用 |
| --- | --- |
| `GET /api/admin/cloud-accounts` | 返回账号状态、脱敏身份、登录方式和续期能力 |
| `POST /api/admin/cloud-accounts/{provider}/login-sessions` | 创建连接、重新授权或更换账号会话 |
| `GET /api/admin/cloud-accounts/{provider}/login-sessions/{id}` | 读取当前管理员拥有的登录状态及展示二维码所需信息 |
| `DELETE /api/admin/cloud-accounts/{provider}/login-sessions/{id}` | 取消登录会话 |
| `POST /api/admin/cloud-accounts/{provider}/check` | 受限频率地检查连接并执行必要续期 |
| `POST /api/admin/cloud-accounts/{provider}/credential-import` | 高级手动导入，经身份校验后保存 |
| `DELETE /api/admin/cloud-accounts/{provider}/connection` | 断开本系统连接，保留历史任务 |

所有接口要求管理员权限，状态接口不接受其他管理员的会话 ID。浏览器只收到展示二维码和账号状态需要的信息，refresh_token、Cookie、上游轮询密钥和设备签名留在服务端。账号操作沿用现有请求保护，并补齐同源及 CSRF 检查。

登录和凭证接口设置 `Cache-Control: no-store`，日志仅记录脱敏身份、平台、结构化状态码和耗时。上游 API 及验证链接限定为已知官方域名；不开放任意请求头或登录地址。

## 9. 实施顺序

1. **认证链路验证**：逐家核实扫码交换、凭证刷新和设备会话契约；先验证官方身份与目录读取。业务写操作用明确选择的测试目录和测试分享单独验证，记录每家实际支持能力。
2. **统一凭证底座**：加密存储、账号身份与版本、刷新租约、历史任务归属映射及旧格式迁移；业务入口接入有效凭证读取。优先解决 Cookie 更新导致归属变化的问题。
3. **可用扫码流程**：优先接入通过第一阶段验证的夸克、阿里、光鸭链路和统一弹窗，再接入百度、迅雷。未通过联调的平台保留真实的备用登录方式，不显示虚假的“自动续期”。
4. **后台维护和恢复**：处理令牌轮换、挑战状态、停机恢复、多实例续期，以及认证等待清理任务的恢复。
5. **界面收尾和升级交付**：替换现有 Cookie/JSON 主配置表单，保留高级导入；更新部署密钥、恢复步骤、账号维护说明和运行监控。

首个可交付版本必须同时具备连接入口、持久化、续期/失效检测和任务衔接，不能以“能显示二维码”作为完成。全部五家支持情况按真实联调结果发布。

## 10. 验收标准

- 新账号只需扫码、选择目录和启用功能即可使用；支持自动刷新时不要求周期性手填字段。
- 前端、错误响应、普通日志和明文数据库列不包含 Token/Cookie。
- 令牌到期后能真实获取新令牌，持久化轮换刷新令牌，重启后仍可继续续期。
- 并发请求和两个服务实例只发起一次有效刷新；旧响应和旧扫码会话不能覆盖新授权。
- 同账号重新扫码及 Cookie 更新不丢失缓存或清理归属；不同账号不能接管旧任务。
- 取消、二维码过期、拒绝授权、短信/验证码挑战、限流、网络中断都有可理解的状态。
- 认证等待不耗尽清理重试次数；同账号恢复后能继续已确认进度；归属异常仍然阻塞。
- 已发送写请求遇到超时或认证相关失败，不因刷新而自动重复写入。
- 取链保持现有响应窗口，登录和刷新不会使请求无限等待。
- 使用模拟上游验证并发和失败场景；逐家真实账号验证身份、目录和跨有效期续期。转存、分享及清理在专用测试目录验证。记录来源、日期和验证结果，不把模拟测试当作平台可用证明。
