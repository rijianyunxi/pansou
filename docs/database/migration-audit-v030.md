## 合并方案

已整理 `schema-v030-reference.sql`，直接展示最终的表、约束、函数、触发器和索引，省去阅读中间版本的反复建删。该文件从空库重放生成，不含实际用户、账号、链接、提取码或业务数据。

它只是结构参考：没有默认配置行、SQLx 迁移记录，也没有旧数据转换逻辑。不要用它初始化应用库后再直接启动现有程序，否则 SQLx 会把该库视为尚未执行历史迁移。应用初始化继续使用 `migrations/`。

如果未来确实需要缩短新库初始化，可以增加专门的基线机制：新库使用最终 DDL 加经核对的默认数据，再由程序建立匹配的历史迁移记录；旧库沿原迁移链升级。实现时还需覆盖中途版本升级、重复启动、校验和验证、数据转换与回滚，不能简单把 30 个 SQL 拼接后替换目录。

## 保留的数据升级限制

- 006/008 会拒绝与保留名称冲突的旧代理配置，不是同名表 DDL 冲突。
- 012 删除被旧业务定义为非管理频道的历史记录；它是历史数据切换步骤，不能在已有库重复手工执行。
- 017、020、024、029 都涉及回填或重算；使用最终结构快照无法替代这些已有数据处理。
- 026 将旧 JSON 参数写入受约束的类型化列。其配置回填依赖 `link-delivery` 与 `link-check` 两行同时存在；正常迁移 011 会创建这两行，若旧库被人工删除过其中一行，应在升级前补齐/核对。参数超出新约束范围也需要先处理。当前库已成功经过该迁移，这不是当前结构冲突。
- 005 的单频道运行唯一索引会拒绝同频道已有多条 running 任务；正常升级应停止旧 worker，处理旧租约后再切换。
