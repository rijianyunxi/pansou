# TG 资源采集与本地搜索：需求设计

- 日期：2026-09-29
- 状态：历史需求草案（记录 2026-09-29 设计时点，不代表当前实现状态）。截至 2026-09-30，代码已具备采集 worker、消息持久化和 TG 本地搜索；新的后台重构方案见 `docs/tg-crawl-workbench-design.md`。
- 技术基础：当前项目实际使用 Rust + Vue 3 + PostgreSQL + Redis，不是 MySQL。
- 原则：沿用 SearchResult 和搜索接口契约；采集与实时搜索共用 Rust transform DSL 及清洗实现。

## 1. 目标与边界

把已配置的公开 t.me 频道改为“后台持续采集 → 解析清洗 → 持久入库 → 搜索只查本地”。

一期包含：历史回填、增量同步、近期编辑复查、任务管理、质量检查、PostgreSQL 本地查询及 Redis 查询缓存。非 TG 来源保留实时搜索。首页布局和公共搜索字段不改，后台增加采集管理。

不包含：私有频道、绕过访问控制/验证码、下载网盘文件、无限跟随外链、未命中时即时抓取、把非 TG 来源也全部采集。

历史回填只承诺覆盖采集途径实际可访问的范围；不能把“公开网页翻不到更早消息”宣称为“Telegram 全部历史已采完”。实施第一步须用代表频道验证分页、稳定消息标识、最早可见记录和访问限制。若公开网页覆盖不足，再单独评估官方授权接口及凭据管理，不能默认 Bot 可以读取完整历史。

## 2. 已确认的现状与风险

本地检查涉及 src/models.rs、src/transform.rs、src/handlers/search.rs、src/search_cache.rs、frontend/utils/resultMerge.ts 及 migrations。

- 已有统一 SearchResult，可直接作为公共输出模型。
- managed_resources 目前主要供后台管理，未接入公开搜索主流程；应复用并扩展，避免平行建立第二套资源库。
- 当前 TG 清洗依赖少量固定“名称/描述/移动/标签”等分隔词，不能保证所有格式都干净。
- 缺少上游 ID 时，fallback ID hash 包含 keyword；不适合持久资源身份。
- 当前链接识别排除了 TG 域名，但仍接受多数其他 HTTP URL，可能混入论坛、广告、导航链接。
- 前端去重直接去掉 URL hash，可能误合并移动云盘不同分享；需要按供应商规则计算身份。
- 搜索缓存目前在 Rust 进程内；本次 TG 本地搜索使用 Redis 缓存，不能保留两份互不失效的 TG 缓存。

以上是代码检查结论，不代表已经修复。

## 3. 架构与数据流

采集链路：

管理员配置来源 → 持久任务调度 → Rust worker 按代理路由抓取一页 → 保存消息身份与原文 → Rust transform DSL → 统一归一化/校验 → PostgreSQL 事务提交资源、来源关系、进度、索引版本。

搜索链路：

Session/权限/频率/并发检查 → 计算授权来源范围 → 获取数据库索引版本 → Redis 查询缓存 → 未命中查询 PostgreSQL → 统一 SearchResult → SSE。

建议 API 和 worker 独立进程、同一个 Rust 项目共享模块。运行模式及命令在实现时加入 README；本文不把未实现命令当成已有功能。

## 4. 采集行为

### 4.1 来源与频道身份

- resource_sources 明确来源类型和搜索方式，例如 telegram + local，不靠名称含 tg 判断。
- 单独保存标准化频道身份，去掉搜索参数，不能用带 q 的搜索 URL 回填历史。
- 同频道多个来源/用户绑定只采集一份；来源绑定和授权可见性独立保存。
- 有可靠上游频道 ID 时优先使用；只有 username 时，改名/转让需人工确认，不能悄悄混合历史。
- 复用现有代理节点、代理组、路由、熔断及审计。仅访问允许的公开入口，校验 DNS/重定向边界，不跟随分享链接下载。

### 4.2 首次回填

1. 先采最新页，尽早产生可搜索资源。
2. 用上游实际游标逐页向历史方向回填，不假设消息 ID 连续。
3. backfill_cursor 和 incremental_cursor 分开，历史回填不能阻塞新消息。
4. 一页可靠持久化后才推进游标；重启从检查点继续。
5. 支持起始日期、页数、消息数、日请求量限制。
6. 结束原因区分：达到目标范围、无更早可访问页、访问受限、失败、人工暂停。

### 4.3 增量、编辑与删除

- 初始建议每频道 5 分钟检查一次、随机抖动、全局 2～4 个频道并行，同频道最多 1 个抓取任务；后台可配置。
- 增量不只读第一页：持续读取直到已持久化的连续检查点，覆盖一轮新增多页的情况。
- 按 channel_id + message_id 幂等 upsert；raw_hash 与解析版本都没变则跳过。
- 近期 7 天编辑复查，可人工指定更大范围重抓/重解析。
- 发布时间、编辑时间、抓取时间、最后看到时间分列存储。
- 某条消息没出现在最新列表不等于被删除；只有明确证据才标记删除，否则待复核。
- 来源删除/停用不误删其他来源支持的资源；频道暂不可访问不能批量清库。

### 4.4 可靠性与安全

- PostgreSQL 持久保存任务、尝试次数、下次执行时间、租约和游标；Redis 不是唯一进度存储。
- 多 worker 事务领取任务、心跳续租；租约过期的旧 worker 不得提交进度。
- 原文、资源、来源关系、检查点、索引版本在同一页事务中提交。
- 单条解析失败可在原文/错误可靠入库后推进页游标，但必须留可重试记录，不能静默丢消息。
- 数据库写失败不推进进度；重试不生成重复资源。
- 429 遵守重试指示并退避；403/访问限制暂停并提示，不靠轮换代理绕过限制。
- worker 与搜索使用独立并发预算；请求/解析超时、响应体大小、页条数都有上限。
- 原始 HTML 在后台仅安全转义预览，不执行脚本或直接 v-html 渲染。

## 5. 唯一解析与清洗规范

### 5.1 一套实现

原文 → DSL 提取结构化字段/正文分段 → 关联链接与提取码 → normalize_resource → validate_resource → SearchResult。

采集、实时 /api/search、/api/search/json、来源调试都调用同一实现。不能在 worker 里另写一套正则。

source_id/channel_id/message_id/parse_version 是解析上下文；keyword 只用于查询，不参与资源身份和清洗。HTML DSL 应支持当前消息节点自身属性及正文分段，避免取不到消息 ID 后改用标题 hash。

### 5.2 字段规则

| 字段 | 要求 |
| --- | --- |
| id | 持久稳定 string；不依赖 keyword、抓取时间、数组下标、当前描述 |
| name | 简洁标题；剥离标题提示前缀、HTML、分享 URL，不把整篇简介放进来 |
| description | 纯文本简介；无 HTML、分享 URL、独立提取码段、无意义推广导航；与 name 重复或没有正文时为 null |
| links | 分享 URL、type、对应 password；无有效分享链接不进入公开资源库 |
| cloud_types | 从有效 links 推导，去重且排序稳定 |
| datetime | 上游发布时间；输出 YYYY-MM-DD HH:mm:ss（Asia/Shanghai）；未知为 null，不用抓取时间伪装 |
| tags | 资源标签，剔除 plugin:* 等内部运行标记 |
| images | 合法 HTTP(S) 图片 URL，不能携带 HTML/危险 URI |

数据库时间使用 timestamptz；明确来源时区，不能猜测；0001-01-01、非法日期不作为正常时间展示。对外可选字段/null 规则继续匹配现有 SearchResult，不新增 raw_html/message_id 等内部字段。

### 5.3 清洗顺序

1. 保留 DOM 结构、换行、段落、锚点，不能先把全文压成一行。
2. 从 href、裸链、结构化字段提取 URL，并按邻近段落匹配提取码。
3. 链接先进入 links，再从标题/简介移除；不能先删后提。
4. 剥离 HTML、解码实体、清理零宽字符与多余空白；脚本/样式内容直接丢弃。
5. 兼容有/无“名称/描述”前缀、半角全角冒号、多种云盘标签、链接嵌入段落。
6. 只删除 URL 和无意义标签，不能把含 URL 的整段剧情都截掉。
7. 头像、频道链接、导航、广告、论坛用户页不能作为分享链接；云盘用合法域名/子域和分享路径规则，不用任意字符串 contains。
8. 原始 URL 与规范化分享身份分开；不能全局清空 query/hash，移动云盘的 #/w/i/... 必须保留。
9. 多链接的密码分别关联，不确定时 null，不能复制同一密码给全部链接。

### 5.4 多资源消息与去重

- 一部资源多网盘：一个 SearchResult，多条 links。
- 多部资源且有明确标题/段落边界：拆成多个 SearchResult，各自关联简介和链接。
- 无法可靠拆分：待复核，不把整帖第一行套给所有链接。
- 不因同名合并不同资源；不因部分链接重叠就传递性合并整批资源。
- 采集入库按精确分享集合去重并保留 provenance；搜索服务端只追加结果，剩余跨来源重复项由前端按精确分享集合合并，作品级模糊合并不在一期范围。
- 同消息重抓和编辑通过持久映射保持 ID；分段改变时优先匹配历史身份，歧义时复核，不能依赖数组序号。
- 后端与前端链接去重规则必须一致，修正移动云盘 hash 问题，不改页面布局。

## 6. PostgreSQL 数据结构

复用 managed_resources 作为统一资源库，新增来源/原文/任务实体，而不是另建一套对外 TG 资源模型。

| 实体 | 职责 |
| --- | --- |
| resource_sources | 现有配置，增加来源类型、local/live 模式、频道绑定 |
| crawl_channels | 去重频道身份、别名、采集配置、双向游标、同步状态 |
| crawl_jobs | 回填/增量/复查/重解析任务、租约、重试、进度和统计 |
| source_messages | 原始消息，唯一 channel_id + message_id，原文/hash/时间/解析版本及状态 |
| managed_resources | 统一清洗结果、稳定 ID、搜索文档、上下架和人工 override |
| resource_occurrences | 消息分段与资源关系；保留各来源提取字段/链接供编辑后重算 |
| resource_links | 资源分享链接、规范化身份、密码及来源关联 |
| config_revisions | 复用现有版本表，增加本地索引/可见性版本 |

消息编辑时替换该来源的贡献，再按其他有效来源重算；不能永远把旧链接累加留着。人工字段 override 和人工上下架优先，采集不能覆盖。

关系表是链接真源；API JSON 通过统一序列化组装。如有 JSON 物化投影，必须事务维护，不允许双向随意写。

原文保留期限/容量可配置；清理原文后，后台必须提示重解析需重抓，不能承诺无网络重放。来源停用立即影响新查询可见性但不删除历史。

## 7. 搜索、缓存与接口

### 7.1 权限与范围

- 系统搜索仅查启用系统来源；source_ids 与允许来源取交集。
- 自定义频道搜索仅查服务端保存、当前 Session 获准使用的频道，不信任客户端随意提交。
- 频道底层数据可以共用，系统/个人绑定及可见范围必须隔离。
- 用户加频道走验证及有限额后台队列；搜索请求不启动采集。
- 现有人工资源不默认全部公开，迁移时明确发布状态。
- 未采完/未命中返回空结果；采集状态通过频道设置/后台展示，不悄悄回退外部请求。

### 7.2 查询

批量查询授权 TG 来源范围，不改成每个频道执行一次 SQL。

排序：标题精确命中 > 标题词组命中 > 标签 > 简介；同分按发布时间降序、稳定 ID。建议服务端返回上限 200，可配置。total 表示“本次返回的原始资源记录数（包括跨来源重复项）”，不能改为全库命中数量；前端按链接拆卡数是不同口径。

PostgreSQL 承担实际检索，Redis 只做查询缓存。项目已有 pg_trgm，可先测试较长关键词的索引查询；中文单字/双字必须单独基准，不假定默认索引可以处理所有短词。需要时在 PostgreSQL 增加受控字符 n-gram 候选索引并用原文二次过滤；单字查询要有候选预算/超时，禁止无界扫描。最终方案依靠实际 EXPLAIN ANALYZE、容量和并发测试决定，不增加独立搜索引擎。

### 7.3 Redis 查询缓存

- 建议正结果 TTL 60 秒，空结果 10 秒，少量抖动。
- key 包含规范化关键词、授权来源/频道集合摘要、索引版本、可见性版本、排序和上限。
- 命中缓存也先鉴权、限流、获取并发许可；管理员调试缓存与公共结果不混用。
- 数据变更与 PostgreSQL 版本递增同事务；查询读取已提交版本并与结果使用一致快照，再写相应 key。不能依赖数据库提交后 Redis INCR 永不失败。
- 初期全局索引版本保证正确性，旧 key 靠 TTL 回收；高频更新有实际缓存压力时再优化来源版本。
- 同 key 请求合并回源、限制等待，避免缓存击穿。
- 仅缓存操作失败可在已通过安全检查后回源 PostgreSQL；Redis 整体不可用导致 Session/限流无法校验时，仍拒绝请求，不得降级成匿名放行。
- 缓存 SearchResult，不缓存旧 searchLogId/SSE 字节；每次新建日志和 start/complete。

### 7.4 公共接口保持一致

POST /api/search：

- start：intervalMs、searchLogId。
- result：results（现有 SearchResult[]）。
- complete：total。
- error：message。

纯 TG 本地查询一次返回扁平资源批次，不按频道拆分，不包含来源 priority。混合查询时，先完成本地查询并推送一个结果批次，再启动非 TG 外部来源；外部来源保持完成一个推送一个，不等全部完成。搜索服务端不再做跨来源去重，complete.total 统计原始返回记录数，前端计算去重后的展示数量。

GET /api/search/json 仍仅管理员，返回 data.total/results/sources/searchLogId。results 是本地优先、外部随后追加的扁平资源数组；sources 只包含外部实时来源的统计与原始结果，并保留其 priority 排序。纯本地查询的 sources 为 []，TG 不再生成每频道搜索统计或 priority。total 是实际返回的原始记录数，包含跨来源重复项。真实采集耗时和历史代理访问仍只放采集任务详情。

## 8. 管理后台

新增 TG 采集管理：

- 频道状态、采集启停、回填范围、双向游标、最新同步、最早/最新可见消息。
- 消息数、有效资源数、新增/更新/跳过/失败/待复核数及明确口径。
- 最近错误、重试时间、代理节点、解析版本。
- 立即同步、历史回填、暂停/继续、重试、范围重解析、安全原文预览、DSL 预览对比、人工上下架。
- 无法估计历史总量时不显示虚假百分比；区分目标完成和上游历史不可访问。
- 批量重解析先预览，再校验后原子替换。失败不清空旧有效数据；已知不满足新清洗标准的旧数据隔离，不能继续当干净数据公开。
- 所有管理 API 为显式 Axum 路由且仅管理员可用；重复任务明确提示冲突。
- 接口错误使用全局 Toast 和就地错误/重试，不允许保存失败仍报成功。

## 9. 验收标准

### 解析与数据

1. 同原文/DSL/版本，采集、实时搜索、来源调试得到相同 name/description/datetime/links/cloud_types。
2. 所有公开 name/description 无 HTML 和分享 URL；描述不等于完整标题；未知时间为 null。
3. 覆盖实体、多种 HTML 换行、前缀变体、裸链、hash/query、多密码、多资源、无描述、广告、非法日期。
4. 不同移动云盘 hash 分享不会合并，相同分享不重复；消息编辑保持 ID，人工 override 不被覆盖。
5. 原始消息、资源、来源关系可追溯，重复回填/重试不增加重复资源。

### 可靠性与安全

1. 覆盖分页重叠、ID 缺口、一轮新增多页、解析失败、数据库故障、租约过期、worker 重启。
2. 写失败不推进游标，失败消息可恢复，限流退避行为可审计。
3. 系统/个人频道隔离，禁用来源后新请求不可见，缓存命中也必须通过安全检查。
4. Redis 安全状态失败不能放行；仅查询缓存故障的降级可验证。

### 接口与 UI

1. 禁止 API 进程访问 TG 网络仍能完成纯 TG 搜索，mock/网络计数证明 TG HTTP 请求为 0。
2. 仅本地、混合、自定义频道、source_ids、空结果和故障均有契约测试。
3. SSE 字段不变，本地结果不被慢来源阻塞，JSON 统计不伪造网络访问。
4. API 失败、采集失败、保存失败在界面真实可见。

### 性能目标（待实测）

约 100 万条代表性有效资源、记录硬件和索引大小、20 并发：目标纯本地服务端 p95 缓存命中 100ms 内、未命中 500ms 内。单字/双字中文、冷/热缓存、增量写入并行分别报告。目标不是已验证性能，达不到需调整索引、容量或目标，不能用小样本充数。

## 10. 实施顺序与默认决策

1. 建立真实样本，先统一解析清洗、稳定身份和前后端链接去重。
2. 扩展统一资源库、消息关系、事务和版本机制。
3. 少量代表频道验证历史可达性，再实现 worker 回填/增量/编辑复查/恢复。
