## 本轮实现

- 迁移 017 新增紧凑的资源/出现记录检索投影，在写入事务内同步名称、频道、时间、解析状态、人工覆盖和资源可见性。先匹配、去重、排名并选出最多 200 条，再取原始展示 JSON。原文和资源数据不删、不改对外 ID。
- 多词关键词最多使用 8 个必要 gram 预过滤，再校验完整名称；不是截断匹配候选。空内部检索、单字、分隔字母及纯符号仍保持原有结果语义。纯符号路径拆分人工覆盖/普通标题分支，让名称过滤先于关联执行。
- 缓存填充按关键词/规范化频道范围合并；缓存版本与结果读取自同一 REPEATABLE READ 快照。Redis 读写不再占用搜索 SQL 事务，缓存 key 升级到 v3，避免复用旧格式。
- 每个 API 实例最多同时执行 4 个本地数据库搜索；仅该事务设置 `work_mem=16MB`、禁用并行、5 秒 SQL 超时。等待执行槽超过 2 秒或同 key 刷新超过 6 秒返回繁忙错误。已有 Redis 全局请求并发限制继续保留，命中缓存不占执行槽。
- 网盘类型改为事务内维护的实际类型引用计数，重复类型在同一资源内只计一次；禁用资源仍按原管理页面规则计入，软删除排除，恢复/物理删除即时更新。下拉选项直接读取十余行汇总表。
- 仅网盘类型筛选的精确总数直接使用同一计数表；其他筛选总数按条件缓存 30 秒，最多 64 个组合。管理员修改会立即清缓存；采集变化下的缓存总数最多滞后 30 秒。类型选项本身不依赖 TTL。
- 管理页面按实际条件生成绑定参数 SQL，不再用空参数 OR 包裹；先分页窄键，再取完整行，增加 `updated_at,id` 稳定排序，保持现有页码接口。
- 监控的资源/链接有效性与检查健康统计合并为一次聚合，共用 30 秒缓存；任务状态/心跳仍实时。增加最近链接失败及已完成检查任务保留筛选的部分索引。
- 保留迁移 013 的全局锁顺序，但仅真实资源变更失效缓存。零行 UPDATE、相同值 UPDATE、冲突无写入不再递增版本。发生记录展示改变与消息解析状态/时间改变仍会正确失效。
- 重解析按差异更新出现记录，未变化的 JSON 不再删除重建或写入；仅删除新结果不包含的引用。解析失败时保留旧引用但隐藏的规则不变。移除采集路径重复显式 bump，其他设置写入的 bump 保留。
- 管理员提交错误的 cloud_types 类型会得到 400，不让汇总触发器因非数组输入报数据库 500。

## 隔离数据集与限制

性能库从业务库只读复制 397,038 条资源、1,346,154 条消息、1,170,589 条出现记录。资源展示字段与出现记录 JSON 保留；消息 HTML 置空，保留实际解析状态/时间。为了控制复制和测试成本，gram 表仅复制“电影”“三体”的 5,874 条 gram 关联，而非业务库的完整 13.8M 行。

因此执行计划/缓存状态不完全等同业务库，绝不能把本节数字当成已上线效果或固定延迟承诺。旧/新 SQL 使用相同隔离数据；原查询源从当前 HEAD 读取。对照在同一个 PostgreSQL 实例运行，没有清空共享缓存、重启数据库或修改全局参数。

## 数据库执行观察

| 观察 | 旧 SQL | 新 SQL |
| --- | ---: | ---: |
| “电影”首组观察 | 1,554.260ms | 533.615ms |
| “电影”随后交替观察一 | 430.215ms | 124.960ms |
| “电影”随后交替观察二，双方全命中共享缓存 | 102.576ms | 93.985ms |
| “电影”共享块访问数，全命中组 | 99,216 | 37,100 |
| 网盘类型，12 个选项 | 492.835ms | 0.067ms |
| 第 1000 页，20 条 | 44.753ms | 13.141ms |

这些是少量单次观察，不是 P50/P95 压测。首组缓存冷热不同，不能宣称严格冷缓存的固定倍数提升；完全热缓存下搜索时间差很小，主要收益是减少宽表/消息读取及工作量，提高冷数据和并发时的余量。

新“电影”SQL 不再访问 source_messages；完整资源表与原出现记录 JSON 均只访问最终 200 条。候选排序行宽约 95 字节，替代旧关联中约 1,542 字节的宽行；这些搜索观察均无临时文件。

纯符号“!!!”在拆分匹配分支后执行 825.287ms，返回 21 条去重资源，无临时写入。业务库旧路径此前在并行执行时发生共享内存不足，诊断事务单线程超过 8 秒；该失败不能与新隔离库值做同机同数据完整耗时对照。

## 升级成本与部署注意

隔离库实测迁移 016 约 14.3 秒，017 约 50.4 秒，合计约 65 秒。017 的两个检索投影含索引约 78MiB + 422MiB，类型计数约 32KiB；另有新增分页/维护索引。016 的引用汇总额外空间详见频道统计验证。

迁移一次性回填会持有写入锁。实际业务库的存储、后台负载与内存不同，耗时可能更长；升级前备份、留出维护窗口、停止旧 API/worker，再启动新二进制。SQLx 会自动顺序应用未执行迁移；迁移失败会回滚该迁移，服务不会提前监听。

本轮未将 016/017 应用到业务库，也未覆盖 Downloads 中的程序。使用构建产物：
[pansou-api](/Users/song/study/pansou/target/release/pansou-api)。

运行中的 PostgreSQL `/dev/shm` 仍为 256MiB，Compose 配置为 1GiB。本轮期间 Compose 又被改成 `./data/postgres` / `./data/redis` 挂载，而运行容器仍使用 `pansou-postgres` / `pansou-redis` 命名卷；这不是本轮修改，已保留。不要盲目重建容器，先确认数据迁移与实际挂载，否则新配置可能连接到空目录里的新数据库。搜索的事务级单线程限制解决该路径的并行共享内存压力，不表示所有 PostgreSQL 查询都已不受容器限制。
