# 频道列表统计优化验证

验证日期：2026-10-01；macOS arm64，PostgreSQL 18，接口为
`GET /api/admin/crawl/channels?q=&enabled=&page=1&pageSize=20`。

## 原因和实现

原统计在 30 秒进程缓存未命中时读取消息和资源关联，关联解析状态，
再对频道内资源去重。业务库执行计划实测 3.014 / 4.048 秒，
每次约 190 MiB 临时文件写入，存在并行哈希分批和磁盘排序。

迁移 016 一次性回填 `channel_statistics` 和
`channel_resource_references`，随后由数据库触发器在写入事务内维护
消息总数和已解析资源引用计数；只有首次/最后一条已解析引用改变
频道去重资源总数。资源禁用和软删除通过已有的失效资源部分索引
即时从总数中排除。接口不再依赖频道统计的进程缓存。

## 隔离数据集

从业务库复制到新建专用测试库：10 个频道、1,346,154 条消息、
1,170,589 条资源关联，得到 629,147 条频道内去重资源引用。
只保留消息 ID、解析状态、资源 ID、可见性等统计所需字段；
HTML、资源标题和关联 JSON 用空值/固定测试值代替。
因此测试库的旧 SQL 耗时与业务库实测不能直接等同。
完整接口测试还复制了任务和失败页记录，并使用隔离 Redis 数据库。
业务库未执行迁移或修改配置，未替换正在运行的服务。

## 回归

- 默认 Rust 测试通过（62 个）。
- 频道统计测试通过：与旧 SQL 比较重复引用、空频道、失败解析、
  重新解析、禁用/恢复、软删除、资源物理删除、关联移动和事务回滚。
- 12 个并发事务共享资源，新增及并发失败/删除后统计准确。
- 三项 Telegram 采集、调度、搜索和管理员接口隔离集成测试通过。
- Release 编译、修改文件格式检查与 git diff 空白检查通过。
- 严格 Clippy 检查被仓库已有的 9 项告警阻止，涉及缓存、AppState、
  云盘传输、采集和链接交付；本次未扩展修改这些代码。

临时服务停止后删除此次创建的两个隔离测试库；测试未连接业务 Redis。
